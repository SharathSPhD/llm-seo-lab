§02What this project is — and is not Tier 1

A short, blunt scoping pass before the architecture pages. Reproduces the spirit of docs/spec/2026-04-25-llm-seo-lab-design.md and the explicit caveats in docs/limitations.md.

It is

  • A monorepo for a closed-loop AEO product: audit a URL → identify citation gaps → draft a fix as a PR → measure post-merge.
  • A dual-target plugin (Cursor + Claude Code CLI) that ships seven slash-commands plus a Sākṣī SessionStart hook.
  • A Node/TypeScript MCP server exposing 16 tools over POST http://127.0.0.1:7301/rpc, all returning the typed { ok, value } | { ok:false, error } envelope.
  • A Next.js dashboard on the same MCP wire — read-side tools (list_sites, read_latest_audit, list_prs, read_citation_trend) feed it directly.
  • A real-evidence project: PR #1 against SharathSPhD/SharathSPhD.github.io exists and is open today.
  • Subscription-Claude-CLI native. No API keys. Ever. (aeo-sakshi.sh pins this as a witness invariant.)

It is not

  • A SaaS dashboard you can subscribe to — there is no tenant model, no auth, no hosting.
  • A drop-in replacement for Profound, Peec, Goodie, AthenaHQ, Otterly, etc. The reasoning core overlaps; the operational surface (action, not just monitoring) is the wedge — and only one site has been driven end-to-end so far.
  • A real-time citation-tracking platform. track_citations is honest about being a stub; the Playwright crawler is a placeholder. T+14 lift is not measured in v0.2.0.
  • An autonomous publisher. Every action is a PR awaiting a human. The loop's terminal state is next_step: "human_review".
  • A model-trained system. There is no training step. Claude Code CLI is the reasoner; everything else is plumbing.

§08The closed loop, phase by phase Tier 1

Six steps, terminal state next_step ∈ { human_review, no_qualifying_gaps, no_seed_pages, quota_exhausted, buddhi_blocked }. This is the C1 IFR turned into a function.

  1. read_config(site_id) — load data/sites/<id>/config.json (seed_pages, max_gaps_per_pr, repo_path, evidence_policy).
  2. audit_page(page_url) per seed page — Claude CLI returns ranked AuditGap[]; on failure, deterministic fallback-stub keeps the loop alive.
  3. filter + rank — keep only Tier-1 references above min_predicted_lift_pp; sort descending by predicted lift; cap at max_gaps_per_pr (default 3).
  4. generate_brief per surviving gap (Manas) — same fail-open behaviour as audit_page.
  5. Buddhi gate — pratyaksha.detect_conflict against the prior audit; on conflict, sublate_with_evidence; brief is blocked or sublated, never silently overwritten.
  6. open_pr(repo_path, branch, briefs) — clone repo to temp dir, write docs/aeo-briefs/<brief_id>.md per cleared brief, commit as llm-seo-lab[bot], push, gh pr create.

Re-audit after merge closes the loop. In v0.2.0, T+0 baselines are written to each PR body; T+1d / T+7d / T+14d delta capture is on hold until track_citations is real (see §15.1).

§11Adversarial architecture review Tier 1

After v0.1.0-alpha.1, the user explicitly asked the architect-review persona to adversarially audit the project against the original brief. The review surfaced 12 distinct findings; 9 are now fixed, 3 are tracked as honest open items.

Top-level conclusions from the review document:

  • Contract drift across MCP / dashboard / cli-worker — three different ports were live in the same repo; four read-side MCP tools the dashboard called did not exist; the { ok, value } envelope was unwrapped by no client.
  • Plugin proof gap — the plugin existed as files but had never been loaded as a Cursor or Claude Code plugin; commands were unverified.
  • "Phase 7 protocol vs Phase 7 proof" — five protocol files existed; zero real PRs had been opened by the loop.
  • TRIZ + attractor-flow used at the design phase but not at the integration phase — the review recommended re-running them on the Pratyakṣa decision before any integration code landed.
  • Sākṣī invariant unspecified in code — the project's own subscription-only / no-API-key constraint was not enforced anywhere.

The full traceability matrix (all 12 findings → R-phase → file → commit) is in §20.

§15Limitations — verbatim, non-marketing Tier 1

The text below is reproduced verbatim from docs/limitations.md. If a section here disagrees with the README, this section wins.

1. Citation tracking is a stub

The track_citations MCP tool and the Playwright browser automation under mcp/src/clients/playwright.ts are placeholders. They return deterministic synthetic data so the dashboard, the cli-worker, and the analytics pipeline can be exercised end-to-end without hitting real engines.

Why it is still a stub: Each engine (Perplexity, ChatGPT, Gemini, Google AIO, Claude.ai) needs its own session-handling, captcha defense, and answer-extraction logic. We did not want to ship a half-implemented version that produces real-looking-but-wrong data. The cited Phase 6 benchmarking results (benchmarks/runs/local/) are Bernoulli simulations calibrated against the GEO survey midpoint — they are useful for validating the statistical pipeline, not for claiming a real lift number.

Implication for users: the closed loop opens a real PR with real brief content. The T+14 lift measurement step is on hold until the Playwright crawler is real. Mark expected lift in the PR body and revisit manually for now.

2. Audit and brief content can fall back to a deterministic stub

audit_page and generate_brief invoke claude --print. If the Claude CLI fails (timeout, missing binary, non-JSON response), both tools return a deterministic fallback object marked claude_model: "fallback-stub" so the loop can still produce a reviewable PR.

This is a feature: the architecture review explicitly demanded that the loop must always be able to make forward progress and produce something a human reviewer can accept or reject. It is also a caveat: a fallback-stub brief is a Tier-1 templated recommendation, not Claude reading your page HTML.

The first live run (PR #1 in docs/use-cases/P3-live-run-2026-04-25/) landed with stub content because the bare-page_url invocation we sent did not produce a fenced JSON block. Future runs that pass real page_html to audit_page and generate_brief will get real content; the schema is identical either way.

3. The Pratyakṣa Buddhi gate degrades to no-op without uv

If uv is not on PATH when the cli-worker daemon starts, the loop does not crash — it instantiates NoopPratyakshaClient, which always reports "no conflicts, no sublations" and lets every brief through. The loop runner records pratyaksha_available: false in LoopRunnerResult.buddhi so this state is visible after the fact.

4. The Cursor marketplace listing is alpha-only

v0.2.0 ships the dual-target plugin manifest, but the marketplace publication step is intentionally deferred. Install via /plugin marketplace add against the local repo path, as documented in README.md — that is the supported install path until the plugin graduates to a tagged marketplace listing.

5. Only one Phase-7 site has a captured live run

The plan describes five Phase-7 validation sites. This release ships the first real PR against sharathsphd.github.io (PR #1). The pattern reused for the other four is identical — drop a data/sites/<id>/config.json, run scripts/aeo-live-run.mjs --site <id> — but the evidence package is intentionally one site for this sweep.

6. No API-key fallback. Subscription Claude CLI only.

This is a constraint, not a bug. The architecture is structured around the user's Claude Code CLI subscription. Adding API-key fallbacks would change the cost model and the Sākṣī invariant (subscription-only Claude CLI; no API keys, ever) and is out of scope.

7. T+14 citation lift is not measured in this release

Recording T0 baselines is implemented (each PR carries pre_audit_id in its body). Re-running the loop after a PR merges to capture T+1d, T+7d, T+14d deltas is the next round of work and depends on (1) above being un-stubbed.

§22Binding constraints (the real frontier) Tier 2 · Synthesis

Things that, if they change, change the product. Things that, if they don't change, the product cannot move past them.

  1. Subscription-only Claude CLI invariant. Sākṣī forbids ANTHROPIC_API_KEY. This rules out parallel API-keyed back-ends for cost/latency optimisation. Every speedup must come from caching, batching, or model-switching inside the subscription.
  2. Buddhi latency. Today ~120 s/call (§19). The cli-worker / Python Pratyakṣa boundary is the largest single chunk. Parallelising and caching can drop it; replacing it cannot — Buddhi is the post-review-mandated gate (F8 in §20).
  3. Customer PR-review capacity. The whole IFR ("every action is a PR") presumes a human reviewer who can absorb < 3 PRs/day per site without fatigue. The default max_gaps_per_pr = 3 is calibrated to this; for high-velocity sites the multi-PR-per-day mode needs an explicit reviewer-throughput budget.
  4. Claude CLI JSON-block contract. audit_page/generate_brief rely on a fenced ```json block in claude --print output. Today this is brittle — a SIGTERM at 60 s, a slightly different prompt, and the loop falls open to a stub. Hardening this is P0 (§23).
  5. uv on PATH. Without it, Buddhi degrades to no-op (§15.3). The Pratyakṣa MCP being Python is a strength (it's a real library) and a constraint (it adds a runtime dependency to a Node monorepo). The R6 install script handles it; an end-user without uv still runs a degraded loop.
  6. Cursor marketplace cadence. v0.2.0 ships the dual-target manifest but install is still local-path-only (§15.4). Marketplace publication requires a separate review track outside this monorepo's release window.

§28v0.3.0 reorientation — from competitor-gap closing to citation-pull v0.3.0

v0.2.0 answered: given a competitor cohort, close the citation gap. v0.3.0 answers a different question: given any page on any substrate, how do we make AI engines pull it harder over time, regardless of whether it lives on Wikipedia / Reddit / domain-authority real estate? The reorientation is additive — the v0.2.0 /aeo:* loop and PR system stay intact and shipped — and is gated by the same /ralph-loop + TRIZ + attractor-flow + Pratyakṣa pipeline.

The locked decisions for the reorientation are spelled out in docs/v0.3.0/plan.md:

  • Same monorepo, same plugin updated in place. New /pull:* mode is added alongside /aeo:*. Plugin manifests bumped to 0.3.0.
  • Supabase (Auth + Postgres + RLS) replaces the local-dev auth shim in apps/web/lib/auth.ts.
  • Measurement leaves the plugin entirely. track_citations, read_citation_trend, and the Playwright crawler stub are deprecated in product flow; users self-report engine observations on the dashboard.
  • Time-spread state machine. Every transition is human-triggered from the dashboard. The plugin only acts on transitions surfaced by the dashboard.
  • Three real seed use cases: www.technektar.dev (web), technektar.substack.com post (substack), youtu.be/fM2hpqPx8zg (youtube).

The CHANGELOG.md v0.3.0 entry is the canonical inventory. The v0.2.0 entry is unchanged.

  • /dashboard — list of the signed-in user's use cases with current stage, iteration, and last-event timestamp.
