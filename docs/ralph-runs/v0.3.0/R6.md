# R6 — Frontend (multi-user, stage-driven dashboard)

**Status:** GREEN
**Date:** 2026-04-26

## Goal (from plan)

> R6: real Supabase auth in `apps/web`; `/login`, `/dashboard`, `/use-cases`
> CRUD, stage panel with action buttons, user-reported measurement form.

R6 turns the plumbing built in R3 (Supabase schema + RLS + MCP tools) and R4
(substrate adapters) into a usable surface. The dashboard owns one
human-gated state machine per use case; every stage transition is a button
that calls a Next.js server action that calls the right MCP tool.

## Deliverables

### Auth (Supabase magic-link)

| File | Purpose |
|---|---|
| `apps/web/app/login/page.tsx` | Server-rendered login page. In Supabase mode shows the email form + status banners; in local mode tells the user they're already signed in as `local-dev`. |
| `apps/web/app/login/actions.ts` | `signInWithEmail` and `signOut` server actions. `signInWithEmail` calls `supabase.auth.signInWithOtp({ email, emailRedirectTo: <host>/auth/callback })`. |
| `apps/web/app/auth/callback/route.ts` | Handles Supabase's `?code=…` PKCE landing. Exchanges the code for a session cookie via `supabase.auth.exchangeCodeForSession` and redirects to `/dashboard`. Falls back to `/login?error=…` on any failure. |
| `apps/web/components/nav.tsx` | Now async; reads the current user via `getCurrentUserAsync()` and renders the user identity + sign-out form (Supabase) or "Local mode" pill (off). |

The auth shim from v0.2.0 (`apps/web/lib/auth.ts`) was already Supabase-aware
from R3. R6 just wires the UI to it.

### Pages

| Route | What it shows |
|---|---|
| `/` | Marketing-ish landing. If the user is signed in, redirects to `/dashboard`; if Supabase mode is on and the user isn't signed in, redirects to `/login`. |
| `/login` | Magic-link sign-in (above). |
| `/auth/callback` | Supabase code-exchange. |
| `/dashboard` | Use-case list table: title, URL, substrate, current stage chip, current iteration, last-event timestamp. "+ Add use case" CTA. |
| `/use-cases` | Alias of `/dashboard` for nav consistency (redirect). |
| `/use-cases/new` | Create wizard. Auto-detects substrate from URL (`web` / `substack` / `youtube`) with manual override. Server action validates with `isValidUrl` + `detectSubstrate`. |
| `/use-cases/[id]` | The stage panel. Header (title + URL + substrate + stage + iteration); next-action button row driven by `getAllowedTransitions(current_stage)`; recommendations table with "Apply this" inline buttons; applied artifacts; measurements; latest analysis verdict; full stage history timeline. |
| `/use-cases/[id]/measurements/new` | User-reported observation form. Engine select (ChatGPT / Perplexity / Google AIO / Claude.ai / Gemini / You.com / Other), prompt, observed answer, citation_present toggle, position, source_authority, notes, optional screenshot path. The plugin never crawls AI engines — this form is the source of truth. |

### Server actions

| File | Action(s) |
|---|---|
| `apps/web/app/use-cases/new/actions.ts` | `createUseCaseAction` |
| `apps/web/app/use-cases/[id]/actions.ts` | `recommendAction`, `nextIterationAction`, `applyRecommendationAction`, `markRepublishedAction`, `startMeasuringAction`, `markMeasuredAction`, `analyzeAction`, `abandonAction` |
| `apps/web/app/use-cases/[id]/measurements/new/actions.ts` | `recordMeasurementAction` |

Every server action:

1. Resolves `user_id` via `getCurrentUserAsync()` (Supabase session in
   prod, `local-dev` in local mode).
2. Validates inputs and either redirects back with `?error=…` or calls
   into the shared action surface in `apps/web/lib/actions/use-cases.ts`.
3. Calls `revalidatePath` on the affected pages so the panel updates
   without a manual refresh.
4. Redirects to the use-case detail page with `?ok=…` on success.

The shared action surface keeps Supabase-direct writes
(`use_cases` / `use_case_events` / `applications` / `measurements`) and
MCP-mediated writes (`recommendations` / `analyses`) on opposite sides
of one boundary. Server actions don't know which is which — they call
`generateRecommendations`, `applyRecommendation`, `recordMeasurement`,
or `runAnalysis`, and the boundary picks the right path.

## Design notes

- **Local mode still works.** When `LLM_SEO_LAB_AUTH_ENABLED=0` the dashboard
  renders all use-case routes against the synthetic `local-dev` user. This
  preserves the v0.2.0 quickstart and lets contributors poke at R6 without
  setting up a Supabase project.
- **Errors don't 500.** Every server action redirects back with `?error=<msg>`
  on failure — Next.js' default error boundary would have hidden the actual
  validation message behind a generic page. Banners on the destination page
  surface the real cause.
- **Iteration semantics.** "Apply this" carries the iteration as a hidden
  field; "Next iteration" bumps it before generating recommendations. This
  keeps the iteration counter monotonic and makes A/B-within-site
  comparisons trivial later.
- **No client-side Supabase.** The browser bundle has zero Supabase SDK
  code; every read goes through MCP `read_use_case_state` and every write
  goes through a server action. This avoids leaking RLS edge cases via the
  anon key in the browser.
- **`/sites/*` archive intact.** v0.2.0 routes still mount as a "v0.2.0
  archive" tab. Their tests still pass; their data dir is untouched.
