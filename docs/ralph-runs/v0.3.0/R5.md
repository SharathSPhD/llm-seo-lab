# R5 — Plugin commands & orchestrator (v0.3.0)

**Status:** GREEN

## Goal (from plan)

> R5: add `/pull:recommend`, `/pull:apply`, `/pull:measure`, `/pull:analyze`, `/pull:state` commands and `pull-orchestrator` agent; bump manifests to 0.3.0.

The plugin gains a second top-level command surface (`/pull:*`) alongside the
v0.2.0 `/aeo:*` commands. The new surface is the user-facing entry point for the
citation-pull state machine implemented in R3 (Supabase + MCP) and R4 (substrate
adapters). The orchestrator agent encodes the human-gated transitions so any
caller (CLI or dashboard server action) gets the same backend behaviour.

## Deliverables

### Commands (5 new files under `plugin/commands/`)

| File | Slash command | What it does | MCP tool |
|---|---|---|---|
| `pull-recommend.md` | `/pull:recommend use_case_id=<id>` | Generate one recommendation per charter principle (5 rows) for the current iteration | `pull_recommend` |
| `pull-apply.md` | `/pull:apply use_case_id=<id> rec_id=<id>` | Build the substrate-correct artifact (web PR diff / Substack Markdown / YouTube checklist). Hands off to user; never auto-publishes. | `pull_apply_artifact` |
| `pull-measure.md` | `/pull:measure use_case_id=<id>` | Surface the dashboard URL where the user enters self-reported engine observations. Prints suggested prompts + expected engines. Never crawls AI engines. | (none — informational; uses `read_use_case_state` for context) |
| `pull-analyze.md` | `/pull:analyze use_case_id=<id>` | Run the TRIZ + attractor + Pratyaksha analysis pipeline over the iteration's recommendations + measurements. Persists an `analyses` row. | `pull_analyze` |
| `pull-state.md` | `/pull:state use_case_id=<id>` | Pretty-print the entire stage history, recommendations, applications, measurements, and analyses for a use case. Read-only. | `read_use_case_state` |

Every command:

- Has YAML frontmatter with `name: pull:<verb>`, `description`, `argument-hint`,
  and a minimal `allowed-tools` set (`Bash`-only for tool-driven commands;
  `Bash, Read, Grep, Glob` for `pull:state` to allow inspecting `data/use-cases/`).
- Calls `${CLAUDE_PLUGIN_ROOT}/scripts/aeo-mcp.sh <tool> '<json>'` rather than
  inlining `claude --json` calls — the MCP shim is the single execution boundary.
- Explicitly forbids auto-publishing (`/pull:apply`) and auto-crawling
  (`/pull:measure`), preserving the human-gated workflow contract from
  `docs/v0.3.0/spec.md` §3.

### Agent (1 new file under `plugin/agents/`)

- `pull-orchestrator.md` — reacts to one stage transition at a time. The agent
  is given a `(use_case_id, target_stage)` pair and:
  1. Loads state via `read_use_case_state`.
  2. Verifies the transition is legal (defers to the shared
     `isLegalTransition` from `@llm-seo-lab/shared` — also enforced by
     `record_use_case_event` server-side).
  3. Performs the per-stage backend work:
     - `RECOMMENDED` → `pull_recommend`
     - `APPLIED` → `pull_apply_artifact` for each recommendation
     - `REPUBLISHED` → no backend work (snapshot-only)
     - `MEASURING` → no backend work
     - `MEASURED` → no backend work (the dashboard insertion already happened)
     - `ANALYZED` → `pull_analyze`
     - `ABANDONED` → no backend work
  4. Records the transition via `record_use_case_event` (only when running
     CLI-side; the dashboard records the event itself before invoking the
     plugin, so the agent skips the write when called with `dashboard=true`).
  5. Returns a structured summary; never advances to the next stage.

The agent's hard rules are stamped at the top of the file: never auto-advance,
never publish, never crawl. These match the Sākṣī invariants from
`docs/triz/v0.3.0-pratyaksha-deltas.md`.

## Design notes

- **Why one tool per command, not a batch RPC?** Each command maps 1:1 to a
  named MCP tool. This keeps the surface inspectable (a developer can discover
  what the plugin does by reading `plugin/commands/`) and lets the dashboard
  bypass the `.md` layer and call MCP directly without re-implementing the
  protocol.
- **Why no `pull-apply` MCP write?** The artifact is generated server-side but
  the user is the one who pastes/PRs it. Writing an `applications` row would
  imply the dashboard has confirmed the page is live, which only the human
  knows. `applications` is written by the dashboard's "Mark applied" button via
  `record_use_case_event` + a measurement-form-style insert, not by the plugin.
- **Why no "next iteration" command?** Iteration bumps happen on the
  `ANALYZED → RECOMMENDED` transition recorded by the dashboard. The plugin
  reads the bumped iteration on its next `/pull:recommend` call. We resisted
  the temptation to add `/pull:next-iter` — the dashboard owns iteration
  identity.

2. The orchestrator agent's `dashboard=true` mode is the call shape the
   dashboard uses (no double-recording of events).

   inline (PR diff = monaco-style block; markdown = paste-ready Markdown panel;
   YouTube checklist = checkbox list).
