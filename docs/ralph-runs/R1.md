## What R1 was supposed to fix

The 2026-04-25 adversarial architecture review flagged the following as P0 contract drift between the `apps/web` dashboard, the `cli-worker` daemon, and the `mcp/` server:

1. Two HTTP transports were live in the same repo — `apps/web` posted to `:7374/mcp`, `mcp/src/transports/http.ts` served `:7301/rpc`, and `cli-worker` defaulted to a third URL. No client could reliably reach the server.
2. `apps/web` actions called four read-side MCP tools — `list_sites`, `read_latest_audit`, `list_prs`, `read_citation_trend` — that did not exist in the registry.
3. The MCP server returned a `{ ok, value }` / `{ ok: false, error }` envelope that no client was unwrapping. Tool errors silently surfaced as “undefined” to UI consumers.
4. `packages/cli-worker/src/runners/loop.ts` invoked tools with stale arg names (`site_id` instead of `page_url` for `audit_page`, etc.).
5. There was no end-to-end HTTP test that booted the server and exercised every tool over the wire, so all four issues above were invisible to CI.

## What R1 actually did

### 1. Standardised the MCP HTTP transport on `POST /rpc` at port 7301

- `apps/web/lib/mcp-client.ts` `DEFAULT_MCP_ENDPOINT` → `http://localhost:7301/rpc` (was `:7374/mcp`).
- `packages/cli-worker/src/mcp_client.ts` `HttpMcpClient` defaults to `http://127.0.0.1:7301/rpc` and also honours `LLM_SEO_LAB_MCP_URL`.
- `mcp/src/server.ts` CLI now defaults to port `7301` when neither `--port=` nor `LLM_SEO_LAB_MCP_PORT` is set, and accepts `--data-dir=` / `LLM_SEO_LAB_DATA_DIR`.

One transport, one path, one default port across web + cli-worker + MCP. Verified by `mcp/tests/integration.http.test.ts` boot log and by the smoke run.

### 2. Added the four missing read-side MCP tools

`mcp/src/tools/index.ts` now registers and exports:

- `list_sites` → enumerates `{dataDir}/sites/<site_id>/config.json`
- `read_latest_audit` → reads the newest audit and aggregates a `SiteAuditSummary` plus `recent_gaps`
- `list_prs` → reads `{dataDir}/sites/<site_id>/prs/*.json` newest-first
- `read_citation_trend` → builds a per-engine citation share trend per `(site_id, topic)` from snapshot files
- `read_config` was extended to accept either `{ site_id }` (resolved against `dataDir`) or `{ config_path }` for back-compat.

Tool count: **12 → 16**. Verified in `mcp/tests/server.test.ts` and on the wire by the new integration test.

### 3. Threaded `dataDir` through `ToolContext`

- `mcp/src/types.ts` `ToolContext` gained `dataDir: string`.
- `mcp/src/server.ts` initialises it (default: `${cwd}/data`) and logs it on startup.
- All four new read-side tools resolve their on-disk paths through `ctx.dataDir`, so production and tests share the same convention.

### 4. Unwrapped the `{ ok, value }` envelope at every client

- `apps/web/lib/mcp-client.ts` `call()` now unwraps `{ ok: true, value }` to bare `value`, and throws `McpHttpError` with the original `AeoError` code on `{ ok: false, error }`. Falls through unchanged for non-tool responses (`tools/list`, `ping`).
- `packages/cli-worker/src/mcp_client.ts` `HttpMcpClient.call()` does the same and throws a typed `McpToolError` carrying `code`, `actionable_next_step`, `retry_after_seconds`. The runner can now branch on `QUOTA_EXCEEDED` etc. instead of pattern-matching messages.
- New `apps/web/lib/mcp-client.test.ts` cases pin the contract:
  - unwraps `{ ok: true, value }` to bare value
  - returns raw result for non-tool methods (e.g. `tools/list`)
  - throws `McpHttpError` on JSON-RPC level error
  - throws `McpHttpError` on tool-level `{ ok: false, error }` envelope

### 5. Aligned the cli-worker loop runner to the real MCP schemas

`packages/cli-worker/src/runners/loop.ts` was rewritten:

- Reads `SiteConfig` via `read_config({ site_id })`.
- Iterates `cfg.seed_pages` (new optional field; falls back to `[cfg.site_url]`) and calls `audit_page({ page_url })` per page.
- Filters gaps by `evidence_policy.require_tier1_first` + `min_predicted_lift_pp`, sorts by predicted lift, caps at `cfg.max_gaps_per_pr` (defaults to 3).
- Drafts one brief per surviving gap via `generate_brief({ gap, page_url, page_html, repo_path })`.
- Opens a single PR via `open_pr({ repo_path, branch, brief_id, pr_title, pr_body })` whose body lists every gap and links each brief.
- Returns a `LoopRunnerResult` with `next_step ∈ { human_review, no_qualifying_gaps, no_seed_pages, quota_exhausted }`.

Five runner tests in `packages/cli-worker/src/runners/loop.test.ts` cover: happy path filtering Tier-1 above threshold, empty-filter early return, `max_gaps_per_pr` cap, `seed_pages` fallback to `site_url`, multi-page audit fan-out.

### 6. Extended `SiteConfig` to support the loop

`packages/shared/src/types/config.ts` `SiteConfig` gained two optional fields:

- `seed_pages?: string[]` — URLs the loop runner audits each tick.
- `max_gaps_per_pr?: number` — defaults to 3.

Optional, so all existing site configs remain valid.

### 7. Wired the in-process HTTP integration test into CI

- New `mcp/tests/integration.http.test.ts` boots the MCP server in-process on a random port with a freshly seeded `dataDir`, then exercises every registered tool via `fetch` to `POST /rpc`. Six test cases cover `tools/list`, the four new read-side tools roundtripping the envelope, `emit_schema`, `track_citations` + `compare_competitors`, `read_repo_metadata` + `read_results`, and the `-32601` unknown-tool path.
- New `mcp/tests/site_readers.test.ts` adds focused unit tests for the four read-side tools against a temp `dataDir`.
- `.github/workflows/ci.yml` `ts-typecheck-test` job now runs three explicit tripwires after `npm run test`: the HTTP integration test, the cli-worker loop schema test, and `npm run smoke`. Any of them failing keeps the merge red.
