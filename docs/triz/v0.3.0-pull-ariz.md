# ARIZ-85C session — C-Pull-1 *substrate-authority deficit vs retrieval-fit*

**Phase:** v0.3.0 R2 · **Date:** 2026-04-26 · **Selected contradiction:** **C-Pull-1 — substrate-authority deficit vs retrieval-fit** (IFR 4/4 in [`v0.3.0-pull-contradictions.md`](v0.3.0-pull-contradictions.md))

ARIZ-85C is the 9-part Algorithm of Inventive Problem Solving. We use it here against the contradiction that defines v0.3.0: the user owns a page on a *low-domain-authority* substrate (an indie .dev, a Substack post, a YouTube video) and wants AI engines (ChatGPT, Perplexity, Google AIO, Claude, Gemini) to cite it more often *without* the page first having to climb domain-authority mountains it cannot climb.

This is genuinely a different ARIZ pass from the v0.2.0 ARIZ in [`ariz-session.md`](ariz-session.md), not a rebrand. The v0.2.0 ARIZ's resolution was *PR-as-product against competitor gaps*. The v0.3.0 ARIZ's resolution is *citation-pull lattice against engine retrievers* and is independent of any competitor.

## Part 1 — Analysis of the problem

**Mini-problem statement.**
> A page hosted on a low-authority substrate (indie domain / Substack / YouTube) is systemically under-cited by AI engines compared to higher-authority substrates (Wikipedia, Reddit, news outlets), even when the page's content is more specific, more recent, or more correct on the actual question. We want a system that **increases citation pull from any substrate** by changing what the page *is* to engine retrievers, **without** depending on domain authority and **without** scraping engines or auto-publishing.

**Conflict pair.**
- Tool A — *Substrate freedom*: The user publishes anywhere they want — git-backed, Substack, YouTube, hosted CMS — and the substrate is fixed by their distribution choice.
- Tool B — *Citation likelihood*: AI engines, in early 2026, weight domain priors heavily. The lower the substrate's authority, the lower the citation likelihood for any given page on it.

**Mini-problem framing (TRIZ form).**
> If the page changes its *retrieval-fit* (what engines actually score on at the embedding layer) to a degree that overcomes the domain-authority discount, then the substrate-authority deficit becomes irrelevant (good — closes the citation-pull gap) — **but** retrieval-fit changes can degrade the page's value to humans (bad — the page becomes machine-friendly but loses voice, narrative, surprise) **and** retrieval-fit cannot be auto-verified without scraping engines (worse — auto-verification re-introduces the ToS / automation problem v0.3.0 explicitly removed).

## Part 2 — Analysis of the problem model

**Operating Zone (OZ).** The page itself, as it exists on the substrate. For technektar.dev: HTML + JSON-LD + internal-link graph. For technektar.substack.com: post body Markdown + post meta + author profile. For YouTube `fM2hpqPx8zg`: title + description + tags + chapters + pinned comment + end-card text. The conflict plays out *inside* the page's own surface area; nothing else is in the OZ.

**Operating Time (OT).** The interval between publication and observable engine citation — *not* a single moment. Specifically: the time from `REPUBLISHED → MEASURED` in the v0.3.0 state machine, which is days to weeks depending on the engine. The OT is *long and external*; the system cannot compress it.

**Resources available** (ARIZ wants every resource enumerated; we list the v0.3.0 set):

| Resource | What it offers |
|---|---|
| The page's own surface (HTML/Markdown/YouTube fields) | The only OZ where the system can act |
| The user's content authority on the topic | The only "authority" the substrate's domain authority cannot dispute |
| Claude Code CLI subscription | The reasoning engine; flat-cost; substrate-uniform |
| Q-shaped subhead lattice (TRIZ #17) | A free axis that engines retrieve along |
| JSON-LD `FAQPage` / `Article` blocks (TRIZ #24) | A free intermediary that maps canonical content into engine-readable schema |
| Atomic snippet density (TRIZ #26) | A free "Wikipedia-style citable unit" pattern any substrate can emit |
| Semantic-anchor stability (TRIZ #28) | Anchors that survive rewrites |
| Substrate-specific adapter (web/substack/youtube) | The artifact emission shape |
| User's own AI-tool subscriptions (ChatGPT, Perplexity, …) | The legitimate measurement channel |
| Supabase (multi-user, RLS) | The intermediary store for measurements + state machine events |
| The Pratyakṣa epistemic harness (Sākṣī, Sublation, Manas/Buddhi) | The discipline that keeps the loop honest across iterations |
| The user's review attention | The only authorisation channel for republication |

**Key insight.** The page's surface is small but *fully writable* by the user. The system does not need new infrastructure to change retrieval-fit; it needs the right *pattern* to apply, the right *artifact* to produce, and a discipline to ensure each iteration learns from the prior. Every resource needed is already on the user's side of the boundary.

## Part 3 — Definition of IFR and Physical Contradiction

**IFR-1 (functional ideality).**
> The page itself, by its own structure, *causes engine retrievers to choose it*, in the operating zone (the page surface), during the operating time (the post-republish window), without depending on the substrate's domain authority and without the system needing to scrape engines or auto-publish.

**X-resource candidate.** The Q-shaped subhead lattice + atomic snippet density + cross-engine intermediary, *together*, are the X-resource. Each alone is insufficient (Wikipedia has them by accident; bare blogs have them not at all); together they constitute a substrate-portable *retrieval-fit profile* that is independent of domain authority.

**Physical Contradiction (PC).**
> The page must **be machine-optimised** (atomic, dense, lattice-shaped, intermediary-equipped) to maximise engine retrieval-fit, AND must **be human-natural** (voice, flow, surprise, story) to retain the substrate-specific audience that brought the user to that platform in the first place — simultaneously, in the same page, on the same surface.

This is the canonical PC form: opposite values of the same property (machine-friendliness vs human-friendliness) at the same time and place.

## Part 4 — Mobilization and use of substance-field resources

The PC is resolved by **separation in space within the page** — different *layers* of the same page serve the two opposite needs.

**Layer split** (this is the heart of the v0.3.0 inventive resolution):

- **Lattice layer** — Q-shaped subheads (`<h2>What is RAG context dilution?</h2>`, `<h3>How do you measure it?</h3>`). Engine-retriever-shaped. Substrate-portable.
- **Snippet layer** — atomic, complete units under 120 words, each immediately following its Q-subhead. Has origin, scope, evidence, recency. Citable as a self-contained block.
- **Anchor layer** — semantic anchors (named concepts engines find via embeddings, not URL fragments). Survive rewrites; persistent across iterations.
- **Intermediary layer** — JSON-LD `FAQPage` block (web), or pinned-comment digest (YouTube), or post-foot summary block (Substack) — the same canonical content rendered into the engine-preferred schema for that substrate.
- **Voice layer** — the prose between subheads. Substrate-authentic: clinical-and-cited on web, conversational-and-anecdotal on Substack, scripted-and-timestamped on YouTube. Voice is *not* compressed by the lattice; it lives between snippets and the engine retriever does not score it.

The page, as a whole, is *machine-optimised AND human-natural* simultaneously, because the layers do not fight each other — engines score on the lattice/snippet/anchor/intermediary layers; humans read the voice layer; the layers cohabit in a single page.

| **#13 The Other Way Around** (invert the direction of action) | Stop pushing the page out to engines (sitemaps, ping endpoints, link-building campaigns). ## Part 6 — Application of the Solution to the Original Problem

**Resolved problem statement.**
> The v0.3.0 system, on each user-triggered `Recommend` action, applies the five-principle citation-pull charter (Atomic-Snippet Density · Semantic-Anchor Stability · Q-Shaped Subhead Lattice · Cross-Engine Intermediary · Inverted Retrieval Target) to the user's page through the substrate-appropriate adapter (web/substack/youtube), produces a substrate-native artifact (PR diff / paste-ready Markdown / YouTube Studio checklist), the user manually applies and republishes, the user observes citation behaviour on their own engine subscriptions, the user reports observations into Supabase, and the system analyses those reports against the prior iteration to recommend the next move. The substrate-authority deficit is mooted because the page is being chosen on retrieval-fit, which the user controls.

**Worked example.** *Use case U2 — technektar.substack.com (post: "When the context window is big and...")*

The recommend step proposes:
- **Lattice:** rewrite the existing thematic subheads as Q-shapes — `Why does context dilution matter when the window is large?`, `How does retrieval interact with a 1M-token window?`, `What happens to attention precision past 200k tokens?`
- **Density:** under each subhead, an atomically-complete snippet with origin (paper / arxiv / repo), scope (which models, which context lengths), evidence (specific finding), recency (when measured).
- **Anchors:** semantic anchors `context_dilution_at_long_window`, `retrieval_at_long_window`, `attention_precision_decay` — each addressable by the engine's retrieval embedding regardless of paragraph reordering.
- **Intermediary:** a post-foot block that renders the lattice as a paste-friendly FAQ digest (Substack does not auto-render JSON-LD on author posts, so the intermediary is a *visible* FAQ section with the same Q-shape).
- **Inversion:** no link-building, no cross-post strategy — the post itself is what engines reach for; the user just reposts the URL once on social, then waits.
- **Voice:** the Substack-authentic conversational tone is preserved between snippets — the user's "let me tell you why this matters to me" voice is the connective tissue.

The user copies the artifact into the Substack editor, republishes, and over the next 1-3 weeks observes engine responses in their own ChatGPT / Perplexity / Google AIO sessions, pasting observations into the v0.3.0 dashboard.

This is what no SOTA tool ships as of 2026-04-26: a substrate-portable, lattice-driven, user-owned-measurement citation-pull discipline.

## Part 7 — Analysis of the Solution

**Does it eliminate the original contradiction?** Yes. The page becomes machine-optimised AND human-natural in the same surface, because the layers cohabit (lattice, snippet, anchor, intermediary, voice). The substrate-authority deficit is dissolved because retrieval-fit is what engines actually score on at the embedding layer.

**Does it introduce a new contradiction?** Three smaller ones:

1. **Voice drift** — over many iterations, the lattice/density discipline can erode the voice layer. *Mitigation:* the v0.3.0 PRD explicitly names the voice layer as protected; every recommendation must specify which existing prose it preserves verbatim and which it touches. Pratyakṣa Buddhi gates this (see [`v0.3.0-pratyaksha-deltas.md`](v0.3.0-pratyaksha-deltas.md)).
2. **Engine-prior unmovability** — for some engines on some queries, the domain prior dominates and no amount of retrieval-fit moves the citation. *Mitigation:* the dashboard is honest about this — the user can see per-engine citation rates over time, and an engine that is unmovable for a use case is reported as such in the analysis output, not papered over.
3. **Sample size on user-reported measurements** — humans can only do so many engine queries per week. *Mitigation:* `pull_analyze` reports `signal_strength` and refuses to declare wins on thin data; iteration N+1 gets recommended only when iteration N has at least the threshold sample (default 3 observations across 2+ engines, configurable).

**All three new contradictions are smaller than the original** and have explicit mitigations grounded in resources already available (the prose voice layer, dashboard state, signal-strength gating).

## Part 9 — Generalisation / forward use

The C-Pull-1 resolution generalises in two directions:

1. **More substrates.** Anything the user can fully edit qualifies (LinkedIn long-form posts, Medium, Ghost CMS, dev.to, Notion public pages). The adapter pattern means a new substrate is one new adapter, not a new product. v0.4.0 will likely add LinkedIn + Ghost.
2. **Multi-page strategy.** Today's v0.3.0 use case is one URL. A future v0.5.0 could treat a *site* as a use case — applying the lattice across many pages with cross-page semantic anchors. The current design does not preclude this; it just doesn't yet implement it.

The resolution does *not* generalise to:

- **Pages on substrates the user does not control** (a New York Times article about the user's product). v0.3.0 explicitly excludes this; `out of scope` in the plan.
- **Pages whose content is not the user's** (linkbait pages on someone else's domain). The five-principle charter assumes the user can rewrite the page, not just request changes to it.
