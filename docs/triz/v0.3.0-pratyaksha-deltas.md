# Pratyakṣa deltas — v0.3.0 citation-pull

**Phase:** v0.3.0 R2 · **Date:** 2026-04-26 · **Anchors:** [`docs/decisions/2026-04-26-pratyaksha-integration.md`](../decisions/2026-04-26-pratyaksha-integration.md) (v0.2.0 R3 baseline), [`v0.3.0-pull-contradictions.md`](v0.3.0-pull-contradictions.md), [`v0.3.0-pull-ariz.md`](v0.3.0-pull-ariz.md), [`docs/decisions/2026-04-26-citation-pull-charter.md`](../decisions/2026-04-26-citation-pull-charter.md), [`docs/v0.3.0/architecture.md`](../v0.3.0/architecture.md).

This file enumerates the changes to the Pratyakṣa integration *between* v0.2.0 and v0.3.0. The v0.2.0 R3 decision adopted **Sākṣī**, **Sublation-with-evidence**, and the **Manas / Buddhi** pair, and consumed Avacchedaka + Boundary compaction transitively. v0.3.0 carries those forward but **updates the witness invariants** to v0.3.0 semantics, **adds Buddhi gates** specific to the citation-pull charter, and **introduces new sublation conditions** for the iteration-keyed store.

The Pratyakṣa harness itself is unchanged — we still consume `pratyaksha-context-eng-harness` as a sibling MCP server, not a re-implementation in our repo. What changes is the *contract* the AEO loop uses with that harness.

## 1. Witness invariant set — v0.3.0 update

### v0.2.0 Sākṣī invariants (carried forward)

The v0.2.0 R3 invariants in `plugin/hooks/aeo-sakshi.sh` were:

```
- subscription-only Claude CLI; no API keys
- audit precedes brief; brief precedes PR
- no synthetic citations
- never overwrite a prior recommendation — sublate it
```

These four remain valid for the `/aeo:*` loop on git-backed sites. They are not removed.

### v0.3.0 additions to Sākṣī

For the new `/pull:*` loop, **five additional invariants** are pushed at session start:

```
- never fabricate engine observations — every measurement comes from a user-pasted artifact
- citation-pull recommendations cite at least one charter principle
  (atomic_snippet_density / semantic_anchor_stability / q_shaped_subhead_lattice /
   cross_engine_intermediary / inverted_retrieval_target)
- no recommendation proposes link-building, sitemap firehoses, or IndexNow ping campaigns
  (Inverted Retrieval Target — negative principle)
- the page surface is the only operating zone — no recommendation touches engines, third-party
  sites, or platforms outside the use case's substrate
- iteration N+1 must read iteration N's measurements and analysis; recommendations are never
  iteration-amnesic
```

Together, the v0.2.0 four + v0.3.0 five form **nine** invariants pushed at session start when the active loop includes `/pull:*` commands. The hook in `plugin/hooks/aeo-sakshi.sh` is updated to carry the v0.3.0 set; the v0.2.0 invariants are unchanged where they overlap.

## 2. New Buddhi gates for citation-pull

The v0.2.0 R3 Buddhi gate fires between brief generation and PR open, calling `pratyaksha.detect_conflict` and `pratyaksha.sublate_with_evidence`. v0.3.0 adds **three new Buddhi gates**, each at a specific place in the `/pull:*` flow:

### Gate G1 — Pre-recommend: charter-principle adherence

Fires inside `pull_recommend` before the recommendation set is returned. Buddhi verifies:

- Every recommendation has `principle_ids` non-empty and all entries are from the charter set.
- No recommendation has tags / wording that signal link-building, sitemap-firehose, ping-bombing, or guest-post outreach (Inverted Retrieval Target negative principle).
- The recommendation set's substrate matches the use case's substrate (no cross-substrate leak).

If Buddhi fails G1, the recommendation set is returned with `partial: true` and the failed recommendations are dropped, never silently overwritten. The dropped set is recorded as a sublation event.

### Gate G2 — Pre-apply: voice-layer protection

Fires inside `pull_apply_artifact` before the artifact is materialised. Buddhi verifies:

- The recommendation's prose changes (if any) do not delete or substantively rewrite the user's voice-layer prose without an explicit `voice_change_authorised: true` flag set on the recommendation.
- The lattice / density / anchors / intermediary changes are *additive* or *replace explicitly tagged structural elements* — not "rewrite the entire post in our voice".

If Buddhi fails G2, the artifact is not materialised; the recommendation is flipped to `needs_user_authorisation` and surfaced in the dashboard for the user to either authorise voice change or trim the recommendation.

### Gate G3 — Pre-analyze: signal-strength sufficiency

Fires inside `pull_analyze` before an analysis is committed to the `analyses` table. Buddhi verifies:

- The use case has at least N measurement rows from at least M distinct engines for the current iteration (defaults: N=3, M=2; configurable per use case).
- The measurements are not all in the same `citation_present=false` direction without engine-rejection notes (i.e. there's some signal to analyse, not a flatline of nulls).
- The analysis's verdict cites at least one TRIZ charter principle and one attractor-flow metric — never a generic "improvement noted" string.

If Buddhi fails G3, the analysis is returned with `verdict: insufficient_signal` and the use case stays in MEASURED stage. The dashboard surfaces "gather more observations" rather than the system making things up.

## 3. New Sublation conditions — iteration-keyed store

The v0.2.0 R3 Sublation contract was:

> Every overwrite of a recommendation IS the audit trail entry that supersedes it. The "loss of information" harm becomes the audit trail resource.

v0.3.0 extends this with **iteration-keyed sublation**: every Pratyakṣa store entry now carries an `iteration` integer pointing to the use case's iteration counter at the moment of insertion.

### New sublation conditions

| Condition | When it fires | Sublation reason |
|---|---|---|
| **Iteration retraction** | A recommendation in iteration N is contradicted by iteration N+1's analysis | `iteration_n_contradicted_by_n+1` |
| **Anchor retirement** | A semantic anchor introduced in iteration N is dropped in iteration N+M because no engine retrieval ever resolved against it | `anchor_did_not_pull_after_M_iterations` |
| **Voice-change reversal** | A voice-layer change authorised in iteration N is reverted in iteration N+1 because the audience-side analytics dropped | `voice_change_reversed_by_audience_signal` |
| **Substrate-prior override** | An engine repeatedly fails to cite the page despite full charter compliance for ≥ 3 iterations on a use case | `engine_X_dominated_by_substrate_prior` |

Each sublation event lands as a row in pratyakṣa's qualified store (Avacchedaka), tagged with `tag: iteration_${use_case_id}_${iteration_index}`, and is queryable by `pull_analyze` when reasoning over iteration history.

### Why iteration retraction is *Blessing in Disguise* (TRIZ #22) at v0.3.0

Each failed iteration is not a regression — it is *evidence the next iteration uses to choose a different charter combination*. The retraction event is the audit-trail signal that informs `pull_analyze` to weight charter principles differently on the next iteration. A use case with 3 retractions on `cross_engine_intermediary` is not a use case where the intermediary is bad in general; it is a use case where the intermediary is bad on *this engine for this substrate* and the analysis can say so explicitly.

## 4. Manas / Buddhi role split — unchanged

The v0.2.0 R3 Manas / Buddhi pair carries forward unchanged in shape:

- **Manas** drafts the recommendation set via a single `claude --print` call. Fast. Cheap. May produce charter-violating proposals.
- **Buddhi** verifies via the three v0.3.0 gates above, plus the original v0.2.0 conflict-detect / sublate path. Slow. Strict. Ratifies or rejects.

The split is what makes the Speed-vs-Precision contradiction (v0.2.0 C1 carried forward) dissolve at the v0.3.0 layer too — Manas only owes speed; Buddhi only owes accuracy.

## 5. What is *not* changed

- **Avacchedaka qualified store**: still consumed transitively. Sublation writes into pratyakṣa's qualified store via `context_insert`. We do not re-implement an AEO-specific store.
- **Boundary compaction**: still consumed transitively. Pratyakṣa's `boundary_compact` runs at the engine layer.
- **Khyātivāda heuristic classifier**: still deferred. v0.3.0 does not introduce evidence that Buddhi alone misses the contradictions.
- **Budget gauge**: still deferred. Subsumed by `boundary_compact`'s budget tracking.

## 6. Implementation contract for R3-R5

The v0.3.0 R2 Pratyakṣa contract decomposes into:

### R3 (MCP + Supabase)

- `mcp/src/tools/index.ts` — the new `pull_recommend`, `pull_apply_artifact`, `pull_analyze` tools call the corresponding Buddhi gates G1 / G2 / G3 inline. Each gate failure produces an explicit envelope (`{partial: true, dropped: [...]}` for G1; `{needs_user_authorisation: true}` for G2; `{verdict: insufficient_signal}` for G3) — never a silent pass-through.
- `apps/web/lib/supabase/*.ts` — the `iteration` column on `recommendations`, `applications`, `measurements`, `analyses` is set on insert from `use_cases.iteration`.

### R4 (substrate adapters)

- `plugin/scripts/adapters/{web,substack,youtube}.ts` — each adapter respects the voice-layer protection (G2 will refuse to materialise an artifact that violates voice). The adapter's `applyArtifact()` returns the artifact + a `voice_change_diff` field so Buddhi can score the diff.

### R5 (plugin commands + Sākṣī hook update)

- `plugin/hooks/aeo-sakshi.sh` — pushes the v0.3.0 nine-invariant Sākṣī set when the active loop includes `/pull:*` commands.
- `plugin/commands/pull-recommend.md` — surfaces G1 partial-recommendation envelopes to the user.
- `plugin/commands/pull-apply.md` — surfaces G2 voice-authorisation prompts to the user.
- `plugin/commands/pull-analyze.md` — surfaces G3 insufficient-signal verdicts to the user.

## 7. Verification

The v0.3.0 Pratyakṣa contract is consistent with:

- The IFR sentence in [`docs/v0.3.0/prd.md`](../v0.3.0/prd.md): "Every observation is human-supplied" maps directly to Sākṣī invariant #5 ("never fabricate engine observations").
- The state machine in [`docs/v0.3.0/architecture.md`](../v0.3.0/architecture.md): G3 fires at the MEASURED → ANALYZED transition; G1 fires inside RECOMMENDED; G2 fires inside the APPLIED → REPUBLISHED arc.
- The substrate adapter interface in [`docs/v0.3.0/spec.md`](../v0.3.0/spec.md): the `Recommendation` type carries `principle_ids`, `voice_change_authorised`, and `iteration` fields that exist precisely to make G1 / G2 / G3 expressible.
- The charter in [`docs/decisions/2026-04-26-citation-pull-charter.md`](../decisions/2026-04-26-citation-pull-charter.md): the five charter principles are the only valid values for `principle_ids`.

**Gate verdict:** pass. The v0.3.0 Pratyakṣa contract is fully specified. Its implementation lands in R3 (MCP), R4 (adapters), and R5 (plugin + hooks).
